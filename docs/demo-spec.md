# 브레인빌리지 데모 기획 스펙 v2.2

> 2026-08-22 기획 검토 회차에서 확정. 구현 착수는 디자인 파일 수령 후.

## 1. 개요

고령자 대상 **동작 기반 인지훈련** 기능성 콘텐츠. 마을에서 미니게임을 골라 플레이하며 인지 훈련을 수행한다.

| 항목 | 내용 |
|---|---|
| 플랫폼 | 웹 (Vite + React + TypeScript) |
| 동작 인식 | MediaPipe Tasks `PoseLandmarker` |
| 인원 | 2인 협동 (경쟁 없음) |
| 운영 환경 | 행사 부스, 진행요원 상주 |
| 데모 범위 | 메인 → 마을 → 튜토리얼 → 오락가락 운동회 1종 |

## 2. 화면 플로우

```
메인 (로고 + 시작)
  └─ 마을 (게임 선택, 아이콘 4~5개 / 미구현은 "준비중")
       └─ 튜토리얼 (게임별 상이)
            ├─ ① 아바타 선택 (할아버지 / 할머니, 참가자 직접)
            ├─ ② 위치 잡기 (카메라 강제 ON, 좌우 분할선 안내)
            ├─ ③ 캘리브레이션 (양손 최대한 들기 3초)
            └─ ④ 무채점 연습 3~5구령
                 └─ 오락가락 운동회 본 플레이
                      └─ 결과 (팀 점수 + JSON 다운로드)
```

- 마을 화면 선택은 **마우스/터치** (진행요원 상주 전제)
- 아이콘 호버 시 확대 + 게임 설명 노출

## 3. 오락가락 운동회

### 3.1 기본 구조

- 좌측 **1P**, 우측 **2P**
- 시작 시 청기/백기 역할 **무작위 배분**
- **2라운드 × 10구령 = 총 20구령**, 라운드 사이 역할 교체 안내 구간
- 구령 시퀀스는 **고정** (난이도 커브 보장 + 참가자 간 비교 가능)
- 지시 후에는 항상 손을 내림 → "내려" 계열 구령은 없음

### 3.2 사이클 타이밍

```
[구령 발화: 오디오 실제 길이 1.0~3.0s] → [반응 창: 2.0s] → [피드백: 1.0s]
```

- 반응 창은 **발화 종료 시점**에 열림
- 라운드 소요 ≈ 50~60초 / 총 플레이 ≈ 2분 / 튜토리얼 포함 4~5분
- 발화 길이는 녹음 파일 실측값을 상수로 고정

### 3.3 난이도 레벨

| 레벨 | 형태 | 예시 |
|---|---|---|
| L1 | 단일 지시 | `청기 들어!` |
| L2 | 좌우 지정 | `백기 왼손 들어!` / `둘다 오른손 들어!` |
| L3 | 페이크 (물음표) | `청기 들어?` |
| L4 | 복합 (부정 결합) | `청기 들지말고 백기 들어!` |

배분: **L1 7 · L2 6 · L3 4 · L4 3**

### 3.4 확정 구령 시퀀스

**1라운드** — 1P = 청기, 2P = 백기

| # | Lv | 구령 | 1P 기대동작 | 2P 기대동작 |
|---|---|---|---|---|
| 1 | L1 | 청기 들어! | 양손 | — |
| 2 | L1 | 백기 들어! | — | 양손 |

| 4 | L1 | 청기 들어! | 양손 | — |
| 5 | L1 | 둘다 들어! | 양손 | 양손 |
| 6 | L2 | 청기 왼손 들어! | 왼손 | — |
| 7 | L2 | 백기 오른손 들어! | — | 오른손 |
| 8 | L3 | 청기 들어**?** | — | — |
| 9 | L2 | 둘다 왼손 들어! | 왼손 | 왼손 |
| 10 | L3 | 백기 오른손 들어**?** | — | — |

**2라운드** — 역할 교체: 1P = 백기, 2P = 청기

| # | Lv | 구령 | 1P 기대동작 | 2P 기대동작 |
|---|---|---|---|---|
| 11 | L1 | 백기 들어! | 양손 | — |

## 4. 판정

### 4.1 동작 판정

| 항목 | 규칙 |
|---|---|
| 좌우 기준 | **사용자 신체 기준** (내 왼손), 화면은 거울 모드 |
| 임계선 | 캘리브레이션으로 측정한 **개인 최대 손목 높이의 70~80%** |
| 유지 시간 | 0.2~0.3초 (단발 노이즈 방지) |
| 2인 인식 | 프레임을 **좌/우로 분할**해 각 영역에 단일 포즈 추정 |

좌우 분할 방식을 택한 이유: `numPoses: 2`는 두 사람이 겹치거나 한 명이 프레임을 벗어날 때 플레이어 ID가 스왑되어 채점 전체가 무효화될 수 있다. 분할 방식은 플레이어 귀속이 물리적으로 보장되고, ROI가 작아 추론 비용 증가도 상쇄된다.

### 4.2 채점

| 구분 | 규칙 |
|---|---|
| 플레이어별 판정 | 기대동작(`NONE` / `양손` / `왼손` / `오른손`) 대비 정·오 |
| 비호명 플레이어 | **참으면 정답으로 카운트** (억제 통제가 핵심 과제) |
| 양손 요구에 한 손만 | 오답 (로그에는 `부분수행`으로 별도 기록) |
| 조급반응 (발화 종료 전 반응) | **오반응** |
| 팀 점수 | 2명 정답 **5점** / 1명 **3점** / 0명 **1점** |
| 만점 | 20구령 × 5점 = **100점** (최저 20점) |
| 화면 표시 | **팀 통합 점수 1개만** — 개인 점수는 노출하지 않음 |

최저점 20점은 의도된 격려 설계다. 고령자 참가 자존감 유지 및 부스 상황을 고려한 결정.

### 4.3 로그 전용 지표

구령마다 다음을 기록한다.

```
{
  구령ID, 레벨, 대상, 기대동작(1P/2P),
  플레이어별 정오,
  반응속도(ms)   // 발화 종료 → 손목 임계선 통과
  오류유형        // 누락(무반응) | 오작동 | 오손 | 부분수행 | 조급반응
}
```

- 반응속도는 반응이 정답인 문항에서만 정의 (무반응 정답 문항은 집계 제외)
- 결과 화면에 **JSON 다운로드** 버튼 제공

## 5. 아바타

### 5.1 구성

레이어 구조: **아바타 바디 레이어** + 그 위에 **표정 레이어**

| 레이어 | 변형 | 장수 |
|---|---|---|
| 바디 | 2 성별(할아버지·할머니) × 2 깃발색(청·백) × 4 포즈 | **16** |
| 표정 | 5종 (성별 공유) | **5** |

- 포즈 4종: `기본` / `양손들기` / `왼손들기` / `오른손들기`
- 표정 5종: `기본` / `웃음(성공)` / `왼쪽 째려보기` / `오른쪽 째려보기` / `울기`
- 깃발: **양손에 자기 색 깃발 1개씩**. `왼손들기`는 왼손 깃발만 올라감
- 성별은 튜토리얼에서 참가자가 직접 선택

### 5.2 표정 매핑

| 상황 | 1P (좌) | 2P (우) |
|---|---|---|
| 대기 / 구령 재생 중 | 기본 | 기본 |
| 둘 다 정답 | 웃음 | 웃음 |
| 나만 정답 (파트너 오답) | **오른쪽 째려보기** | **왼쪽 째려보기** |
| 나만 오답 (파트너 정답) | 울기 | 울기 |
| 둘 다 오답 | 울기 | 울기 |

째려보기 방향 = 항상 파트너가 있는 쪽. 어느 성별이 1P가 될지 모르므로 좌우 2종이 모두 필요하다.

### 5.3 프로덕션 제약

1. **얼굴 앵커 고정** — 4개 포즈 모두 머리 위치·크기를 동일하게 유지할 것. 포즈별로 몸이 기울면 표정 레이어가 어긋난다. (포즈별로 달리 그릴 경우 포즈별 얼굴 앵커 좌표를 별도 전달)
2. **표정 레이어는 눈·입 파츠만** — 성별 공유이므로 머리 윤곽·머리카락·주름은 바디 레이어에 포함되어야 하고, 두 성별의 눈·입 위치가 동일해야 한다.

## 6. 연출 / 접근성

- **웹캠 화면**: 아바타가 메인 피드백. 카메라 화면은 별도 배치하되 **ON/OFF 토글**. 단 튜토리얼 위치 잡기·캘리브레이션 구간은 **강제 ON**
- 카메라를 끈 참가자도 "얼마나 들어야 하는지" 알 수 있도록, 아바타 옆에 **도달 게이지/링** 별도 표시
- **구령 제시**: 실제 사람 녹음 + 대형 텍스트 + 아이콘 동시 제시
- **페이크 구령**: 억양만으로는 난청 참가자에게 불공정하므로, 화면에 **물음표를 크게** + 지시문 박스 색/테두리 차별화
- **청/백 색상**: 백내장·색약 고려해 명도 차 + 도형/패턴 병행
- **실패 피드백**: 빨간 X, 실패 효과음 등 부정적 연출 배제. 표정으로만 표현하고 색상·사운드는 중립 톤

## 7. 구현 노트

React 렌더 사이클과 게임 루프를 분리해야 한다. 반응속도를 ms 단위로 측정하는 게임이므로:

- MediaPipe 루프 + 판정 로직은 `requestAnimationFrame` + `useRef`(또는 외부 스토어)에서 실행. 프레임마다 `setState` 하면 렌더가 폭주한다
- 타이머는 `setTimeout` 누적 대신 **rAF 타임스탬프 기준**으로 계산
- UI로 올리는 state는 throttle: 현재 구령 / 남은 시간(100ms 단위) / 손 올림 여부(bool) 정도
- `PoseLandmarker`는 GPU delegate, 모델은 `lite`로 시작

## 9. 정식 버전 이관 항목

데모 범위에서 제외하고 정식 버전으로 미룬 것들.

- **협동 연출**: 동시성 보너스(둘 다 정답 + 반응 시간 차 0.5초 이내), 팀 콤보 게이지. 데모는 점수 합산만 유지
- 세션 데이터 **서버 전송** 및 누적 리포트 (데모는 로컬 JSON 다운로드)

**(1) `02_백기` 단어 내부에 240ms 공백**

「백」(70~165ms)과 「기」(421~644ms) 사이가 240ms 비어 있다. 대조군 `01_청기`는 같은 자리가 40ms다. 그대로 재생하면 "백…기"로 끊겨 들린다.

→ 보정: 음절 2개를 모두 살리고 사이 공백만 60ms로 압축해 이어 붙인다. 결과 431ms (청기 493ms와 유사).
→ 주의: 앞의 88ms 덩어리는 잡음이 아니라 **「백」 음절**이다(ZCR 1200~2000의 모음 특성). 잡음으로 보고 버리면 "기 들어"가 된다.

**(2) 클립 간 음량이 최대 3.3배(약 10dB) 차이**

| 올리지 말고 | 0.830 | ×1.02 |
| 들어 | 0.818 | ×1.04 |
| 청기 | 0.742 | ×1.15 |
| 왼손 | 0.567 | ×1.50 |

### 12.4 안내 음성: TTS 제거 (v1.6)

구령 외 안내를 Web Speech API(TTS)로 임시 처리했으나, **기계 음성이 몰입을 깨뜨려 전부 제거했다.** 안내는 화면의 큰 텍스트로만 한다.

제거한 곳 4군데:
- 튜토리얼 3단계 안내 (위치잡기 / 스트레칭 / 캐릭터 선택)
- 연습 시작 안내 — 안내 음성을 기다리던 3.6초 지연도 1.2초로 줄였다
- 역할 교체 안내
- 결과 점수 안내 — TTS 종료 시점에 BGM 볼륨을 올리던 더킹도 함께 제거(진입부터 정상 볼륨)

**대체 조치 2건:**
- 역할 교체는 규칙이 바뀌는 구간인데 무음이 되면 화면 변화를 놓칠 수 있어, 정답 차임과 구분되는 **전환 효과음**(3음 아르페지오)을 넣었다. 음성이 아니므로 몰입을 해치지 않는다.
- 구령 클립 로드가 실패했을 때의 대체 경로도 TTS를 쓰지 않는다. 화면 텍스트를 읽을 시간만 무음으로 확보한 뒤 반응 창을 연다.

§8의 "튜토리얼·안내 멘트 5~6" 녹음을 받으면 위 4곳에 사람 목소리로 채운다. `둘다` 클립이 추가되면 §12.1의 두 번째 결정을 되돌릴 수 있다.

### 14.4 ⚠ 연습: 시간 제한 없이 성공할 때까지

**본게임과 판정 방식이 다르다.** 본게임은 반응 창 2.0초로 끊지만, 연습은 두 사람이 기대 동작을 **동시에 400ms 유지**할 때 통과한다. 조건을 만족하지 못하면 다음 구령으로 넘어가지 않는다(시간 제한 없음).

- 부분수행(양손 요구에 한 손)은 통과되지 않는다 — 검증함
- 비호명 플레이어의 기대 동작은 `none`이므로 가만히 있으면 이미 만족 상태로 표시된다
- 연습은 벌점 개념이 없어 통과 시 정답으로 확정한다(조급반응 판정 미적용)
- 플레이어별로 `따라해 보세요 / 좋아요! 그대로`를 띄워 누가 남았는지 보여준다

### 14.5 카운트다운

`CountDown.mp3`(3.16초)에 소리가 4개 들어 있고 **간격이 1000ms가 아니라 약 910ms**다. 실측 큐(0 / 925 / 1831 / 2770ms)에 3·2·1·시작 이미지를 맞췄다. 측정 오차 25~40ms.

## 16. v1.8 — 휘슬 효과음 반영 (2026-08-25)

`assets/Sound/` 에 진행자 휘슬 2종이 전달되었다. **`.m4a`(AAC)** 형식이며 Chrome에서 정상 디코딩된다(부스가 Chrome 전제라 문제없음).

| 파일 | 전체 | 앞 무음 | 실제 소리 | 원본 피크 | 적용 게인 |
|---|---|---|---|---|---|
| `짧은휘슬.m4a` | 755ms | 126ms | 629ms | 0.451 | ×1.22 → 0.55 |
| `마무리휘슬.m4a` | 1875ms | **481ms** | 848ms | 0.199 | ×3.77 → 0.75 |

두 파일 모두 **앞 무음을 잘라내야** 한다. 특히 마무리휘슬은 앞이 481ms 비어 있어 그대로 재생하면 "끝!" 이미지보다 반 박자 늦게 들린다.

음량 목표치는 음성(0.85)보다 낮게 잡았다. 휘슬은 고음이 조밀해 같은 피크에서도 훨씬 크게 들리고, 짧은휘슬은 구령마다 울려 반복 피로가 생기기 때문이다. **부스 실기기에서 조정할 여지가 있는 값이다.**

### 16.1 배치

| 지점 | 소리 |
|---|---|
| 본게임 GOOD / GREAT 이펙트 (1명 이상 정답) | 짧은휘슬 |
| 튜토리얼 위치잡기 통과 · 캘리브레이션 완료 · 성별선택 | 짧은휘슬 |
| 연습 구령 통과 | 짧은휘슬 |
| 게임 종료 "끝!" 이미지 | 마무리휘슬 |

**기존 합성 비프음(goodChime / greatChime / beep)을 휘슬로 대체했다.** 운동회 연출에 실제 휘슬이 맞고, 사각파 비프와 실제 녹음이 섞이면 어색하다.

GOOD과 GREAT은 같은 휘슬을 쓴다(전달받은 파일이 1종). 구분은 화면 이펙트(GOOD! / GREAT! 이미지)가 담당한다.

**0명 정답일 때는 휘슬을 울리지 않는다** — 휘슬이 긍정 신호이므로, 오답에 울리면 의미가 뒤집힌다. §6의 부정적 연출 배제에 따라 중립 톤만 남겼다.

역할 교체 전환음(3음)은 §12.4에서 넣은 합성음이 그대로 남아 있다. 여기에 쓸 녹음이 있으면 교체 가능하다.


## 17. v1.9 — MediaPipe 포즈 인식 재작성 (2026-08-25)

이 환경은 카메라가 차단되어 있어 포즈 코드가 한 번도 실제로 돌아본 적이 없었다. 전면 재작성하고, 카메라 없이 검증 가능한 부분을 모두 실측했다.

### 17.1 고친 결함

| # | 결함 | 영향 | 조치 |
|---|---|---|---|
| 1 | **visibility 미검증** | MediaPipe는 사람이 없어도 33개 랜드마크를 항상 반환한다. 그대로 쓰면 빈 화면에서도 손을 든 것으로 판정된다 | 코·양어깨 평균 신뢰도 0.6 미만이면 `present=false`, 손 입력 무시 |
| 2 | 손목 가려짐 즉시 해제 | 팔이 몸에 잠깐 겹치면 든 손이 풀린다 | 6프레임 유예 후 해제 |
| 3 | 히스테리시스 없음 | 임계선 부근에서 on/off가 떨려 유지 판정(250ms)이 계속 리셋된다 | 올림/내림 임계를 분리(몸통 크기 비례 ±0.024) |
| 4 | 캘리브레이션이 **절대 최솟값** 사용 | 튄 프레임 하나가 도달 불가능한 임계선을 만든다 | 상위 10% 분위를 최대 도달점으로 사용 |

| 6 | GPU 실패 시 전체 초기화 실패 | 가속이 없는 부스 PC에서 키보드 모드로 떨어진다 | GPU → CPU 자동 대체 |
| 7 | 워치독 인터벌 미해제 | destroy 후에도 계속 돈다 | 핸들 보관 후 해제 |
| 8 | 위치잡기가 **세로만** 검사 | 얼굴 원 옆에 서 있어도 통과된다 | 거울 보정 좌표로 타원 내부 판정 |

### 17.2 실측 (카메라 없이 검증 가능한 항목)

로컬 `wasm` + `pose_landmarker_lite.task`로 초기화·추론이 정상 동작함을 확인했다(빈 화면 검출 0개 = 정상).

| 항목 | 값 |
|---|---|
| wasm 로드 | 20ms |
| 모델 로드 | 626ms |
| 델리게이트 | GPU 성공 |
| **첫 추론 (콜드)** | **최대 4.9초** |
| 안정 구간 추론 | 회당 약 42ms |
| **2인 프레임 비용** | **약 83ms → 약 12fps** |

캔버스 크기는 성능에 거의 영향이 없다(256×288 ~ 640×720에서 37~48ms). 비용이 입력 업로드가 아니라 추론 자체이므로, 정확도를 위해 큰 쪽을 쓴다.

**첫 추론이 최대 4.9초**라 튜토리얼 도중에 겪으면 인식이 멈춘 것처럼 보인다 → 초기화 시 더미 프레임으로 **워밍업**한다.

### 17.3 ⚠ 반응속도 측정 정밀도

포즈 갱신이 약 12fps이므로 §4.3의 `반응속도ms`는 **약 ±80ms의 양자화 오차**를 갖는다. 개인 간 비교나 대략적 경향에는 쓸 수 있으나 절대값으로 해석하면 안 된다. 부스 PC 성능에 따라 달라지므로 `poseEngine.status()`로 현장에서 fps를 확인할 것.

MediaPipe는 메인 스레드에서 돌아 프레임당 83ms를 점유한다. UI 애니메이션과 타이머도 그만큼 거칠어진다. 개선하려면 웹 워커 + OffscreenCanvas로 옮겨야 하는데, 데모 범위를 넘어 정식 버전 과제로 둔다.

### 17.4 판정 로직 검증 (합성 랜드마크)

카메라 없이 `applyResult`에 합성 랜드마크를 넣어 확인했다.

- 사람 없음(신뢰도 0.1) → `present=false`, 손 입력 무시 ✅
- 히스테리시스: 0.350 유지 → 0.360 해제 → 0.310 아직 → 0.300 상승 ✅
- 손목 가려짐: 1회 유예 → 6회 이상 해제 ✅
- 캘리브레이션: 어깨 0.45 / 도달 0.10 → 임계 0.1875. 튄 프레임(0.02)에 오염되지 않음 ✅

### 17.5 부스 현장에서 확인할 것

실기기 웹캠으로만 검증 가능한 항목이다. 개발 모드에서 콘솔에 `__pose.status()`를 치면 아래를 볼 수 있다.

- [ ] `fps` — 12 이상인지 (낮으면 반응속도 오차가 커진다)
- [ ] `delegate` — GPU인지 CPU인지
- [ ] `present` — 두 사람이 각자 반쪽 프레임에 제대로 잡히는지
- [ ] `threshold` — 캘리브레이션 후 값이 어깨보다 충분히 위인지
- [ ] 좌우 귀속 — 화면 왼쪽 사람이 1P로 잡히는지 (거울 모드 확인)
- [ ] 임계선 75%가 고령자에게 과한지 (팔이 잘 안 올라가는 분 기준으로 조정)


## 18. v2.0 — 손 제스처로 화면 조작 (2026-08-25)

타이틀 화면을 **1P 오른손**으로 조작한다. 손 위치로 커서를 움직이고, **주먹을 1초 유지하면 클릭**되며 유지하는 동안 커서 아래에 진행 바가 차오른다.

### 18.1 왜 모델을 하나 더 쓰는가

`PoseLandmarker`(몸 33점)로는 **주먹을 판별할 수 없다.** 손가락 정보가 없기 때문이다. 그래서 메뉴 조작에는 `HandLandmarker`(손 21점)를 쓴다.

두 모델이 동시에 돌지는 않는다.

| 화면 | 사용 모델 |
|---|---|
| 타이틀 (메뉴 조작) | HandLandmarker |
| 튜토리얼 · 게임 (동작 판정) | PoseLandmarker |

카메라는 `camera.ts`가 단독 소유한다. 각자 `getUserMedia`를 부르면 같은 장치를 두 번 열어 실패하거나 프레임이 끊기므로, 스트림·video 엘리먼트를 공유한다. `hand_landmarker.task`(7.8MB)를 로컬에 포함해 오프라인 구동을 유지한다.

### 18.2 설계상 중요한 결정

**커서 기준점은 손끝이 아니라 손바닥 중심(중지 MCP)이다.** 손끝을 쓰면 주먹을 쥘 때 손가락이 접히며 커서가 튀어, 누르려던 곳을 벗어난다. 실측 결과 손바닥 기준에서는 펼친 손 ↔ 주먹 전환 시 **커서 이동량 0**이다.

**활성 영역을 확대한다.** 손을 화면 끝까지 뻗기는 어려우므로 카메라 프레임의 가운데 영역(가로 20~80%, 세로 15~85%)을 화면 전체에 대응시킨다. 적은 움직임으로 전체를 덮고, 바깥은 클램프된다.

**지수 평활**(계수 0.35)로 떨림을 줄인다. 고령자 대상이라 반응 속도보다 안정성을 택했다.

**주먹 판별**은 검지·중지·약지·소지의 끝이 손목에서 PIP 관절보다 가까운지로 본다(3개 이상 접히면 주먹). 손 크기(손목~중지 MCP)로 정규화해 카메라와의 거리에 무관하다.

**클릭 후 손을 펴야 다시 클릭된다.** 주먹을 계속 쥐고 있으면 연속 클릭되지 않는다.

클릭은 `elementFromPoint`로 해당 지점의 요소를 찾아 `click()`을 보낸다. 기존 `onClick` 핸들러가 그대로 동작하므로 화면별 추가 배선이 필요 없다.

### 18.3 ⚠ 손 인식을 인트로 후에 켜면 안 된다

모델 로드 0.8초 + GPU 워밍업 최대 4.8초가 필요하다. 인트로(6초)가 끝난 뒤 시작하면 **커서가 11초쯤 뒤에야 나타난다.** 그래서 타이틀 진입과 동시에 시작하고, 인트로 중에도 커서를 보여준다(인식되고 있음을 알리는 역할). 인트로 중 주먹은 인트로 스킵으로 동작한다.

### 18.4 실측

| 항목 | 값 |
|---|---|
| 모델 로드 | 788ms |
| 델리게이트 | GPU 성공 |
| 첫 추론 (콜드) | 4,794ms → **워밍업 필수** |
| 안정 구간 추론 | 회당 약 47ms (약 21fps) |
| 빈 화면 손 검출 | 0개 (유령 입력 없음) |

진행률 실측: 113ms→0 / 401ms→0.29 / 701ms→0.59 / 1001ms→0.89 / 1300ms→1.0 (선형). 1초 도달 시 1회만 클릭되고, 펴고 다시 쥐면 재클릭된다.

### 18.4b 마우스 커서와 손 커서 일치 (v2.1)

두 커서는 **같은 파일·같은 픽셀 크기·같은 핫스팟**이어야 한다. 처음 구현은 두 가지가 틀렸다.

| 문제 | 원인 | 조치 |
|---|---|---|
| 손 커서 비율 깨짐 | 원본 `Cursor_Idle.png`(362×362 **정사각**)를 120×192로 그려 세로로 늘어났다 | 크롭본을 원본 비율(0.6328)대로 사용 |
| 두 커서가 다르게 보임 | 마우스는 크롭본(`_cur.png`), 손은 원본을 썼다 | 둘 다 `_cur.png` 사용 |

크기는 **81×128**로 통일했다. CSS 커서 상한이 128px이라 그 한계에 맞춘 최대 크기이고(부스 화면을 멀리서 봐도 보이도록), 핫스팟은 (38,0) = 가운뎃손가락 끝이다.

**손 커서는 스테이지 밖에 그린다.** 스테이지에는 `scale` 변형이 걸려 있고, 변형된 조상은 `position: fixed` 자손의 컨테이닝 블록이 되어 배율이 그대로 적용된다. 안쪽에 두면 화면 크기에 따라 커서만 커지거나 작아져 마우스 커서와 어긋난다. 스테이지 배율 0.1875에서도 렌더 크기가 81×128로 고정되고, 지정 좌표 대비 **오차 0px**임을 실측했다.

> 참고: 손 커서는 `requestAnimationFrame`으로 갱신하므로 창이 가려지면 멈춘다. 부스는 항상 화면이 켜져 있어 문제되지 않는다.

### 18.5 카메라 없을 때

카메라를 못 열면 손 조작이 꺼지고 타이틀 하단에 `카메라를 사용할 수 없어 손 조작이 꺼졌습니다 — 마우스로 진행하세요` 를 띄운다. 마우스·키보드 경로는 그대로 살아 있어 부스가 멈추지 않는다.

### 18.6 남은 범위

지금은 **타이틀만** 손 조작이다. 마을 선택도 같은 방식으로 넓힐 수 있다(`useHandControl` + `<HandCursor />` 두 줄). 다만 스펙 §2는 마을 선택을 마우스/터치로 두었고 §9는 동작 기반 UI를 정식 버전 이관 항목으로 두었으므로, 확대 여부는 별도 확정이 필요하다.

**오른손 판별**은 현장 확인이 필요하다. 거울 모드에서 MediaPipe의 handedness 라벨이 뒤집혀 보일 수 있어, 손이 하나만 잡히면 라벨과 무관하게 그 손을 쓴다(메뉴가 멈추지 않도록). 두 손이 잡힐 때만 라벨로 오른손을 고른다. 부스에서 `__hand.status()`로 확인할 것.


## 19. v2.2 — 포인터 구성 변경, 마우스 커서 원복 (2026-08-25)

### 19.1 위치는 포즈, 주먹은 제스처 모델로 분리

기존에는 `HandLandmarker` 하나로 위치와 주먹을 모두 처리했다. 손 랜드마커는 멀리 있는 손을 자주 놓쳐 판정이 늦고, 주먹 여부를 손가락 기하로 직접 계산했다. 역할을 나눴다.

| 역할 | 모델 | 이유 |
|---|---|---|
| **위치** | `PoseLandmarker` 의 오른손 손목(RIGHT_WRIST) | 몸 전체 맥락으로 잡아 멀리서도 안정적. 손목은 주먹을 쥐어도 움직이지 않아 커서가 튀지 않는다 |
| **주먹** | `GestureRecognizer` 의 `Closed_Fist` | 학습된 분류기가 손가락 기하 계산보다 정확. 점수 0.5 미만은 무시해 오탐을 막는다 |

`hand_landmarker.task`(7.8MB)는 제거하고 `gesture_recognizer.task`(8.4MB)를 추가했다.

### 19.2 ⚠ 제스처 모델이 더 느리다 — 주기를 나눠 대응

실측 결과 제스처 모델은 손 랜드마커보다 **2배 느리다.**

| 모델 | 회당 추론 | 비고 |
|---|---|---|
| PoseLandmarker | 42ms | |
| HandLandmarker (제거) | 47ms | |
| **GestureRecognizer** | **87ms** | 로드도 2.7초로 가장 느리다 |

매 프레임 포즈+제스처를 모두 돌리면 129ms(약 8fps)로 커서가 뚝뚝 끊긴다. 그래서 **포즈는 매 프레임, 제스처는 2프레임마다** 돌린다. 커서는 부드럽게 움직이고, 주먹은 1초 유지를 판정할 만큼만 자주 확인하면 된다.

> 위 수치는 **빈 화면(손 없음) 최악값**이다. 손이 실제로 있으면 MediaPipe가 탐지 모드에서 추적 모드로 넘어가 더 빨라진다. 현장에서 `__hand.status()` 의 `fps`를 확인하고, 낮으면 `GESTURE_EVERY`를 3~4로 올린다.

### 19.3 마우스 커서를 기본 커서로 원복

손 모양 커서를 마우스에도 씌웠더니 **손 그림이 두 개 떠서** 어느 것이 자기 커서인지 헷갈렸다. 마우스는 OS 기본 화살표로 되돌리고(버튼 위에서는 `pointer`), 손 그림은 제스처 커서 전용으로 남겨 둘을 확실히 구분한다.

`Cursor_Idle_cur.png` / `Cursor_Selecting_cur.png`(81×128)는 제스처 커서가 계속 사용한다.

### 19.4 검증 (합성 입력)

- 손목 신뢰도 0.1 → 추적 안 됨 ✅
- 손목 검출 → 커서 좌표 0.833 (거울 + 활성영역 매핑) ✅
- `Open_Palm` → 주먹 아님 / `Closed_Fist` 점수 0.3 → 무시 / 0.92 → 주먹 ✅
- 1.1초 유지 → 클릭 1회, 계속 쥐어도 중복 없음 ✅
- 주먹 중 커서 이동량 **0** ✅
