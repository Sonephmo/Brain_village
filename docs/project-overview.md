# 영차마을 프로젝트 분석 및 게임 C 준비 기록

> 아래는 게임 C 구현 **이전**의 분석 기록이다. 이후 추가한 게임 C 흐름·에셋·현재 검증 범위는 [게임 C 구현 기록](game-c-figma-inventory.md)을 기준으로 한다.

분석일: 2026-09-19. 코드 기준: `main`, `7232108` (`게임 B 업데이트`).
코드·기획 문서·Figma 메타데이터와 주요 화면 스크린샷을 읽고 정리했다.
런타임 실행, 카메라 실측, 서버 접속 검증은 이번 분석에 포함하지 않았다.

## 1. 프로젝트의 목적과 현재 이름

- 현재 서비스명은 **영차마을**이다. 사용자가 기존 브레인빌리지에서 변경했다고 명시했다.
- 고령자를 대상으로 두 사람이 몸을 움직이며 참여하는 협동 인지훈련 웹게임이다.
- 행사 부스에서 진행요원이 운영하는 환경을 전제로 한다. 게임 선택, 연습, 본게임, 수행 기록까지 한 앱에 들어 있다.
- 저장소 이름 `Brain_village`, 패키지명 `brain-village`, HTML 제목·일부 화면 대체 텍스트·로그 파일명·기획 문서에는 이전 이름이 남아 있다. 이번 작업에서는 분석 문서만 추가했다.
- 예전 문서에는 변경 이력이 섞여 있다. 현재 동작은 코드로 확인하고, 게임 C의 기획은 이번 대화에서 사용자가 정정한 내용을 우선한다. Figma의 문구·에셋이 모두 확정된 게임 규칙을 뜻하지는 않는다.

## 2. 앱의 공통 흐름

`기관 로그인 → 참가자 2명 로그인 → 타이틀 → 마을 → 위치 잡기 → 캘리브레이션 → 캐릭터 선택 → 게임별 연습 → 본게임 → 결과`

- 기관 로그인은 Supabase Auth와 기관 프로필 조회를 사용하며 기관 정보는 localStorage에 유지된다.
- 개인 로그인은 기관 내 01~99 코드 두 개를 받는다. 두 참가자의 코드는 서로 달라야 한다. 현재는 서버 명부 검증 없이 로컬 형식만 확인한다.
- `App.tsx`의 상태로 화면을 전환한다. 별도 라우터나 전역 상태관리 라이브러리는 없다.
- 마을의 8개 장소 중 학교(게임 A)와 전망대·캠핑장(게임 B)이 활성 상태다.
- 결과의 다시하기는 연습을 생략하고 같은 참가자가 재도전한다. 확인은 마을, 홈으로는 타이틀로 이동한다. 홈으로만 눌러서는 참가자 로그인이 초기화되지 않는다.
- 진행요원은 1번 키로 연습·튜토리얼을 건너뛰고, 본게임에서 2번 키를 두 번 눌러 중단할 수 있다.

포즈·제스처 모델, WASM, 글꼴, 게임 에셋은 `public/`에 포함되어 있다. 게임 처리 자체는 로컬 자원으로 이루어지지만 기관 인증과 서버 기록에는 연결이 필요하다. 로컬 진행요원 진입 경로도 존재한다.

## 4. 동작 인식에서 유지해야 할 규약

- 웹캠은 한 번만 열고 공유한다.
- 게임 중에는 카메라 영상을 좌우 절반으로 나눠 각각 한 사람씩 추론한다. 화면 왼쪽 1P는 원본 카메라의 오른쪽 절반, 화면 오른쪽 2P는 원본의 왼쪽 절반이다.
- 왼손·오른손은 참가자 자신의 신체 기준이다. 플레이어의 좌우 위치와 구분해야 한다.
- 메뉴에서는 전체 프레임으로 커서 위치를 얻고, 게임에서는 두 사람의 포즈를 얻는다.
- 캘리브레이션은 손을 올린 표본을 모아 개인 도달 높이의 약 75%를 일반 손 들기 기준으로 설정한다. 신뢰도 검사와 경계 부근 떨림 방지가 있다.
- `leftRaised`·`rightRaised`는 개인 임계선 통과 여부다. **머리 위까지 들었다는 사실을 직접 보장하는 값이 아니다.**
- 추적이 끊기면 손 들기 값이 false가 될 수 있다. 손이 내려간 동작과 인식 유실을 같은 성공으로 처리하지 않도록 C의 왕복 판정에서 구분해야 한다.
- Q/W는 1P 왼손/오른손, O/P는 2P 왼손/오른손 예비 입력이다. 현재 키보드 입력에는 잼잼 입력이 없다.
- 기존 제스처 엔진은 전체 영상에서 손 하나(`numHands: 1`)의 `Closed_Fist`만 사용한다. 플레이어별 잼잼 횟수는 제공하지 않는다.
- `App.tsx`는 본게임 중 메뉴 제스처 인식을 끈다. 게임 C에서 손가락 인식이 필요하므로, 게임 입력과 메뉴 클릭을 구분하여 제스처 인식을 연결해야 한다.
- 기존 문서의 FPS 수치는 과거 측정 기록이다. 현재 PC에서의 성능이나 두 사람의 잼잼 인식 성능은 아직 측정하지 않았다.

## 5. 기존 미니게임의 구현 수준

### 게임 A — 오락가락 청기백기

- 학교에서 진입. 연습 5개, 본게임 2라운드 × 10구령.
- 현재 코드는 1P 청기·2P 백기로 시작하고 중간에 교대한다. 초기 문서의 무작위 배정 표현과 다르다.
- 단순 구령, 좌우 손 지정, 물음표 페이크, 부정 구령으로 구성된다.
- 녹음 구령 재생 → 반응 창 2초 → 피드백 1초, 역할 교대는 5초.
- React 화면 렌더와 분리된 `GameRunner`가 진행·판정을 담당한다.
- 한 구령에서 두 명 정답 5점, 한 명 정답 3점, 모두 오답 1점. 총 100점 만점.
- 구령별 정오, 누락·오손·부분수행·조급반응 등의 오류 유형과 반응 시간을 기록한다.
- 결과는 팀 점수와 점수 구간별 상품이며, JSON 다운로드와 서버 전송이 연결되어 있다.

### 게임 B — 펄럭펄럭 불피우기

- 전망대·캠핑장에서 진입. 함께 부채질, 왼쪽 사람, 오른쪽 사람, 도깨비불에서 정지하는 연습·이벤트가 있다.
- `FanCounter`는 양손 내림 → 양손 올림 → 양손 내림의 완전한 왕복만 1회로 센다. 자세 유지 기준은 150ms다.
- 현재 초안은 본게임 60초, 6초 이벤트 10개, 이벤트당 왕복 2회, 정지 2초, 팀 성공당 10점이다.
- 연습은 왕복 5회이며 일부 안내 문구도 5회로 작성되어 있다. 본게임 2회 판정과 안내 문구를 구분해야 한다.
- 결과에 개인별 성공 이벤트 수와 최대 5개의 불꽃 평가가 나온다.
- `rulesVersion: draft-1`이며 서버 전송은 없다. 로컬 결과와 JSON 다운로드만 있다.

### 게임 C — 아직 앱에 연결되지 않음

현재 선택 타입은 `flag | campfire`이고, C 전용 화면·판정·결과·에셋 매니페스트는 없다. 기존 공통 준비 단계와 두 사람의 포즈 추적, B의 왕복 카운터 구조를 활용할 여지가 있다.

## 6. 수행 데이터

- A 본게임에서 `session`, 구령당 P1·P2의 `trial`, 역할 교대 `interaction`, 1초 단위 `motion_window`를 보낸다. 세션 종료는 `close_session` RPC다.
- 원본 카메라 영상이나 전체 랜드마크를 전송하는 경로는 이 코드에 없다. 참가자 코드와 파생 수행 지표를 보낸다.
- 전송 설정이 없으면 서버 기록은 꺼지고 게임은 진행된다. 네트워크·서버 실패 일부는 localStorage 큐에 남겨 재시도하며 4xx 거절은 경고 후 버린다.
- `score_delta`는 두 사람의 trial에 동일한 팀 점수로 들어간다. 개인 점수처럼 합산하면 중복 집계된다.
- `logCommand`의 기대동작·오류·인지표적(`T2`)·상호작용(`I6`) 등은 A를 전제로 한다. C의 잼잼·왕복 완료·개별 반응 기록에는 별도 매핑과 서버 스키마 확인이 필요하다.
- `motion.ts`의 일반 손 올림 횟수는 게임 C의 떡 치기 완료 횟수나 잼잼 횟수와 다르다.

## 7. 게임 C의 사용자 확정 사항

| 항목 | 확정 내용 |
|---|---|
| 떡 치는 사람 | 양손을 **들었다가 내리기까지 완료**해야 인정. 올리기만 한 경우 불인정 |
| 떡 정리하는 사람 | 왼손 들기 / 오른손 들기 / 잼잼 3회가 각각 가능한 지시 동작 |
| 역할 교대 | 두 사람이 떡 치기와 떡 정리 역할을 교대 |
| 완성 후 마무리 | 두 사람 모두 양팔을 머리 위로 들기 |
| 재미 요소 | 충돌, 째려보기, 아파하기 등의 재미 연출을 추가하지 않음 |

처음 사진에서 읽은 기본안은 전·후반 약 30초씩, 교대 전 각자 5회씩 총 10회, 1회 정답 5점, 전체 100점, 50점 이상 완성이다. 이후 대화에서는 이 숫자를 바꾸지 않았다. 반응 제한 1.5~2초는 사진에서 제안 범위였으므로 정확한 값은 아직 미정이다.

기록 항목은 개인별 정답·잘못된 동작·무반응 횟수와 반응 시간, 게임 성공 여부다. C에서는 동작을 시작한 시점과 전체 동작을 완료한 시점을 분리해 정의하는 편이 좋다. 이는 구현 제안이며 아직 확정된 측정 규칙은 아니다.

## 9. C 구현 전 구분할 사항

1. **잼잼 판정**: Figma는 양손을 세 번 주무르라고 안내한다. 손별 열림·닫힘, 1회 기준, 두 손의 허용 시차, 추적 유실 처리까지 정의해야 한다. 기존 단일 주먹 클릭 엔진만으로 완성되어 있지 않다.
2. **머리 위 동작**: C의 마지막 동작은 일반 손 들기 기준과 구분해 판정해야 한다. 이를 위한 별도 완료 프레임은 이번 프레임 목록에서 식별하지 못했다.
3. **횟수·시간 배분**: 30초 내 각자 5회, 잼잼 3회, 지시·피드백·교대 시간을 어떻게 묶을지는 아직 코드로 정해지지 않았다.
4. **점수 표시**: 100점 및 성공 기준 50점과 Figma의 5칸 아이콘을 연결하는 방식은 아직 정해지지 않았다. 개인 평가 아이콘과 팀 점수를 별도로 정의해야 한다.
5. **공통 튜토리얼의 차이**: C 시안에는 기본자세 단계가 있으나 현재 공통 튜토리얼은 위치 → 스트레칭 → 선택의 3단계다. C 시안 선택 제목은 성별선택, 실제 안내는 원하는 토끼 선택이다.
6. **연습 범위**: 시안에는 오른손 뒤집기 예시가 있다. 사용자 규칙에는 왼손 들기도 있으므로 실제 연습 구성에서 포함 여부를 정해야 한다.
7. **에셋 표시**: 일부 시안에는 서로 다른 동작 프레임이 겹쳐 보인다. 구현 시 상태에 맞는 프레임을 골라 표시해야 하며, 모든 레이어를 동시에 켜면 안 된다.
8. **진입·음성·기록**: C를 연결할 마을 장소, C 전용 구령 음성, 결과 데이터 구조 및 서버 기록 범위는 아직 연결되어 있지 않다.

## 10. 이번 분석의 범위와 다음 작업 기반

실제 소스와 문서의 차이를 확인하고 Figma의 C 화면 위치를 식별했다. 앱 실행·카메라 정확도·게임 성능·Supabase의 현재 스키마는 검증하지 않았다. 로컬에는 아직 `node_modules`가 없으며 패키지 스크립트에는 `dev`, `build`, `typecheck`, `preview`가 있다.

C를 구현할 때는 공통 카메라·포즈·준비 화면을 활용하면서 C 전용 동작 판정, 역할·구령 진행, 토끼 렌더러, 결과 기록을 추가하는 방향이 적합하다. 현재 문서는 구현 완료를 의미하지 않는다.
