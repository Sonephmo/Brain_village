# Supabase 작업 지침 — 브레인빌리지 개인 리포트

> **읽는 대상:** Supabase 프로젝트를 관리하는 Claude Code 에이전트
> **보내는 쪽:** 게임 클라이언트 (`Sonephmo/Brain_village`, Vite + React + TS)
> **프로젝트 ref:** `rgryouhbopagzsxxnhaf`
> **작성:** 2026-08-26

이 문서를 요청한 사람(교수님)은 SQL을 직접 쓰지 않습니다. **당신이 SQL을 쓰고, 결과를 한국어로 보고**해야 합니다.
파괴적 작업(DELETE·DROP·컬럼 제거) 전에는 대상 건수를 먼저 조회해 보여주고 확인을 받으세요.

## 0. 지금 상태 (모두 실측 확인됨)

**테이블 8개:** `site` · `profile` · `content` · `session` · `trial` · `interaction` · `motion_window` · `report`

**게임 클라이언트의 권한:** publishable 키로 `session`·`trial`·`interaction`·`motion_window` **INSERT만** 됩니다.
SELECT·UPDATE·DELETE는 RLS로 막혀 있습니다. 즉 **클라이언트는 자기가 넣은 데이터를 읽을 수 없습니다.**
그래서 이 문서의 작업 결과 확인은 **전부 당신 몫**입니다.

**세션 종료:** `close_session(p_session_id, p_completed, p_team_score, p_max_score, p_commands_played, p_abort_reason, p_pose_fps)` RPC가 `session`을 닫고 `report` 행을 만듭니다. `boolean` 반환 — 대상이 없거나 이미 닫혔으면 `false`.

**주의 — `report.site_code`는 `site`에 FK가 걸려 있습니다.** 등록되지 않은 `site_code`로 세션을 만들면 종료 시 `409 / 23503`이 나고, 클라이언트는 4xx를 재시도하지 않고 버립니다(`console.warn`만 남습니다). 즉 **팀 점수·완주 여부가 조용히 유실됩니다.** 새 현장 코드를 만들 때는 `site`에 먼저 등록하고 게임 쪽에 알려주세요. 현재 등록된 코드: `demo` (왕복 확인됨).

## 2. 리포트를 만들기 전에 반드시 알아야 할 4가지

### 2.1 한 구령 = `trial` 2행

한 자극(구령)에 두 사람의 판정이 각각 한 행으로 들어갑니다. 같은 자극에서 나온 두 행은 **`unit_id`** (= `{session_id}:{구령ID}`)로 묶입니다.
자극 수를 셀 때는 `count(distinct unit_id)`, 사람별 시행 수를 셀 때는 `actor_code`로 나눠 세세요.

### 2.2 `score_delta`는 **팀 값**입니다 — 개인 점수는 없습니다

한 자극의 획득 점수(둘 다 정답 5 / 한 명만 3 / 둘 다 실패 1)가 **두 행에 똑같이 복제**돼 있습니다.
그냥 `sum(score_delta)` 하면 점수가 **2배**가 됩니다. 팀 점수는 `unit_id`로 중복 제거한 뒤 합치거나, `session.team_score`를 쓰세요.

**개인 점수는 만들 수 없습니다.** 게임 기획이 의도적으로 개인 점수를 비노출로 정했습니다. 개인 리포트는 점수 대신 **정확도·반응속도·오류유형·동작량**으로 씁니다.

### 2.3 ★ 가장 중요 — 실행 시행과 억제 시행을 절대 섞지 마세요

한 사람의 20시행 중 **10개는 "가만히 있어야 정답"** 입니다 (`expected_action = 'none'`).

> 두 종류를 합쳐 정확도를 내면 **아무것도 하지 않은 사람이 자동으로 50%를 받습니다.**
> 실제로 카메라가 꺼진 테스트에서 아무도 움직이지 않았는데 `correct = true`가 정확히 절반 나왔습니다.

반드시 이렇게 나누세요.

| 구분 | 조건 | 사람당 세션 n | 의미 |
|---|---|---|---|
| **실행 시행** | `expected_action <> 'none'` | 10 | 지시에 반응하는 능력 |
| **억제 시행** | `expected_action = 'none'` | 10 | 참는 능력 (이 게임의 인지 표적) |
| └ 페이크 | `stim_type = 'stop'` | 4 | 강한 억제 요구 (「물음표!」) |
| └ 상대 구령 | `stim_type = 'go' AND expected_action = 'none'` | 6 | 선택적 반응 |

### 2.4 사람을 잇는 방법

`session.player_codes`는 **1-based 배열**입니다.

```
actor_code = 'P1'  →  player_codes[1]   (화면 왼쪽 참가자)
actor_code = 'P2'  →  player_codes[2]   (화면 오른쪽 참가자)
```

값은 기관이 부여한 두 자리 번호(`'07'`, `'42'` …)입니다. `'P1'`/`'P2'` 문자열이 들어 있으면 **참가자 미식별 세션**입니다.

`trial.actor_code`와 `motion_window.actor_code`는 사람이 아니라 **화면 좌/우 위치**입니다. 여기에 참가자 번호를 넣지 마세요 — 위치 정보가 사라집니다.

## 3. 만들어 주세요 (우선순위 순)

### 3.1 [높음] 개인 리포트용 VIEW 2개

리포트 앱이 **`SELECT * FROM ...` 한 번으로 끝나게** 뷰로 만들어 주세요. 계산 규칙은 아래에 다 적었습니다. SQL은 당신이 쓰세요.

#### `v_participant_session` — (세션 × 사람) 1행

| 컬럼 | 계산 |
|---|---|
| `site_code`, `session_id`, `started_at`, `ended_at` | `session` 그대로 |
| `participant_code` | `actor_code='P1'` → `player_codes[1]`, `'P2'` → `player_codes[2]` |
| `partner_code` | 반대쪽 |
| `actor_code` | `'P1'` / `'P2'` (화면 위치) |
| `n_act`, `acc_act` | `expected_action <> 'none'` 인 시행 수와 `correct` 평균 |
| `n_inhibit`, `acc_inhibit` | `expected_action = 'none'` 인 시행 수와 `correct` 평균 |
| `n_fake`, `acc_fake` | `stim_type = 'stop'` |
| `rt_mean_ms`, `rt_sd_ms`, `n_rt` | `rt_ms IS NOT NULL` 인 것만 (정답 반응에서만 기록됨) |
| `err_누락` … `err_조급반응` | `error_type` 5종 각각의 개수 |
| `acc_l1` … `acc_l4` | `level` 별 `correct` 평균. **n이 7/6/4/3뿐이라 참고용** |
| `team_score`, `max_score`, `commands_played`, `completed`, `abort_reason` | `session` 그대로 — **팀 값임을 컬럼명으로 드러내세요** |
| `rep_total`, `cadence_mean`, `lift_max`, `active_ratio_mean`, `symmetry_mean`, `sway_mean` | `motion_window`를 같은 `actor_code`로 집계 |
| `windows_used`, `windows_dropped` | **`presence_ratio >= 0.5` 인 창만** 평균에 쓰고, 제외한 창 수를 세세요 |

`windows_dropped`를 세는 이유: 사람이 인식되지 않은 초를 0으로 섞으면 평균이 거짓이 됩니다. 그리고 **버린 초 수를 리포트에 표시**해야 「데이터가 깨끗한 것」처럼 보이지 않습니다. (`motion_window`에 `windows_dropped` 컬럼은 없습니다 — 뷰에서 계산하세요.)

`participant_code`가 `'P1'`/`'P2'` 인 행은 **뷰에서 제외**하세요. 참가자 미식별 세션입니다.

#### `v_participant_trend` — (기관 × 사람) 1행

| 컬럼 | 계산 |
|---|---|
| `site_code`, `participant_code` | |
| `n_sessions`, `first_session_at`, `last_session_at` | |
| `acc_act_first` / `_last` / `_delta` | 첫 세션 대비 마지막 세션 |
| `acc_inhibit_first` / `_last` / `_delta` | 같은 방식 |
| `rt_mean_first` / `_last` / `_delta` | 같은 방식 |
| `rep_total_mean` | 세션 평균 |

**리포트 화면에 반드시 함께 표시할 경고:** 사람당 한 세션이 **20시행**(실행 10 / 억제 10, 페이크 4)입니다.
셀당 3~10개로는 신뢰구간이 지표 차이보다 넓습니다. **단일 세션으로 「이 사람의 인지 능력」을 말할 수 없습니다.**
말할 수 있는 것은 「이번에 이렇게 했다」이고, 여러 세션이 쌓였을 때 **추세**입니다. `n_sessions`를 리포트에 항상 노출하세요.

#### 뷰 권한

**뷰에 `anon` SELECT를 열지 마세요.** 인증된 운영자(`authenticated` + `profile.site_code` 일치)만 자기 기관 데이터를 보게 하세요.
Postgres 뷰는 기본적으로 소유자 권한으로 돌아가 RLS를 우회하므로, `security_invoker = true` 로 만들거나 기관 필터를 뷰 안에 넣으세요.

### 3.2 [높음] `participant` 로스터 + 번호 검증 RPC

**왜 필요한가:** 게임의 개인 로그인은 참가자가 두 자리 번호를 직접 누릅니다. 지금은 **`42`가 `24`의 오타인지 확인할 방법이 없습니다.** 통계보다 이 입력 사고가 개인 리포트 신뢰도를 더 크게 위협합니다.

```
participant
  site_code   text          -- site 참조
  code        text          -- 두 자리, '01' ~ '99' (0 채움)
  active      bool  default true
  note        text          -- 기관 내부 메모 (개인정보 금지)
  created_at  timestamptz
  PK (site_code, code)
```

그리고 **존재 여부만** 돌려주는 함수를 만들어 주세요. 명단 전체는 절대 노출하지 마세요.

```
verify_participant(p_site_code text, p_code text) returns boolean
  -- 등록되어 있고 active 이면 true
  -- anon 에 EXECUTE 허용 (게임 클라이언트가 부릅니다)
```

만들어 주시면 게임 쪽에서 개인 로그인에 붙여 **미등록 번호를 즉시 거부**하게 하겠습니다. 지금은 1~99 범위 검사만 합니다.

> 개인정보는 넣지 마세요. 실명·생년월일·연락처는 게임이 받지도 않습니다. 기관이 부여한 번호만 씁니다.

### 3.3 [중간] `trial`에 `round` · `role` 컬럼 추가

지금 라운드와 역할이 DB에 없습니다(`round`·`role`·`block`·`phase` 전부 없음을 확인). 그래서 「청기일 때 vs 백기일 때」 비교를 하려면 **리포트 앱이 게임 관례를 하드코딩**해야 하고, 게임 구성이 바뀌면 조용히 틀린 리포트가 됩니다.

```
ALTER TABLE trial
  ADD COLUMN round smallint,
  ADD COLUMN role  text;          -- '청기' | '백기'
```

**CHECK 제약은 걸지 마세요.** 이유는 §5의 배치 원자성 경고를 보세요. 컬럼만 만들어 주시면 게임이 채워 보냅니다.

기존 행 백필은 선택입니다. 현재 게임 구성의 규칙은 이렇습니다 — 확신이 없으면 `NULL`로 두세요.

```
round = (trial_index / 10) + 1     -- 한 라운드 10구령, 총 2라운드
1라운드: P1 = 청기, P2 = 백기
2라운드: P1 = 백기, P2 = 청기      -- 라운드 사이에 교체 (interaction I6 로 기록됨)
```

## 4. 전달 문서 정정 2건

`6_선모_전달_실시간전송_적용안내_20260826.md` 의 내용 중 **실제 DB와 다른 것**이 있습니다.

| 값 | 실측 결과 |
|---|---|
| 누락 · 오작동 · 오손 · 부분수행 · 조급반응 | **전부 통과** |
| 색 · 위치 · 규칙 | 거부 (`23514`) |

문서 §5의 「게임 어휘 그대로 간다」가 맞습니다. **DB는 고칠 것이 없고, 문서를 고쳐야 합니다.**

§3.1처럼 **뷰에서 계산**하는 쪽을 권합니다 — 컬럼을 새로 만들면 게임 클라이언트도 고쳐야 합니다.

## 5. 하지 말아야 할 것

**`anon` / publishable 롤에 SELECT를 열지 마세요.** 지금 이 키가 공개 저장소의 클라이언트 번들에 박혀 있어도 데이터가 새지 않는 **유일한 이유**입니다.

**`service_role` 키를 게임 클라이언트나 저장소에 넣지 마세요.** `Sonephmo/Brain_village`는 **공개 저장소**입니다.

**`trial`·`motion_window`·`interaction`에 `anon` UPDATE/DELETE를 열지 마세요.** 로그는 append-only여야 하고, 클라이언트는 재전송으로 멱등성을 확보합니다(PK가 클라이언트 생성 UUID).

**기존 CHECK 목록에서 값을 빼지 마세요.** 게임이 보내는 값이 거부되면 그 행이 조용히 사라집니다.

### ★ 배치 원자성 — 제약을 추가할 때 반드시 게임 쪽에 알려주세요

PostgREST 배치 INSERT는 **한 문장**입니다. 게임은 `trial`을 **2행씩**, `motion_window`를 **10행씩**(5초 × 2인) 보냅니다.

> 새 `CHECK`·`NOT NULL`·`FK`를 추가하면, **한 행이 위반해도 그 배치가 통째로 사라집니다.**
> 클라이언트는 4xx를 재시도하지 않고 `console.warn`만 남기므로 부스에서는 아무도 모릅니다.
> 하필 가장 분석 가치가 높은 행이 유실되는 형태입니다.

제약을 추가·변경하기 전에 게임 쪽에 알려주세요. 우리가 보내는 값이 통과하는지 먼저 확인합니다.

## 6. 작업 후 확인해서 알려주세요

클라이언트는 SELECT를 못 하므로, 아래는 **당신만 확인할 수 있습니다.**

- [ ] §1 테스트 행이 지워졌는지 (삭제 전 대상 건수를 먼저 보고)
- [ ] 실제 플레이 세션이 몇 건 쌓였는지, `site_code` 별 분포
- [ ] `session.player_codes`에 두 자리 번호가 제대로 들어오는지 (`{'42','99'}` 형태)
- [ ] `trial`이 한 자극당 정확히 2행인지 (`unit_id` 별 `count(*) = 2`)
- [ ] `session.completed`·`team_score`가 채워졌는지 (= `close_session`이 성공했는지)
- [ ] `report` 행이 세션마다 1건 생기는지
- [ ] **유실 흔적** — `unit_id` 별 행이 1개이거나, 세션 길이에 비해 `motion_window`가 10의 배수로 비어 있으면 배치가 거부된 것입니다
